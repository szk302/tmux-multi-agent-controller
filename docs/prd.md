## 1. システム概要

### 1.1. 目的

tmac は、フックを持つ対話型の AI CLI（Claude Code など）を tmux のペインで起動し、CLI のフックから状態を受け取って、入力できるときだけ入力する CLI である。人はいつでもペインを見て割り込むことができ、人が割り込んでいる間、tmac は自動の入力を止める。

ワークフロー（Dagu）、manager AI、人の手作業のどれからも、同じコマンドで呼び出せる部品として動作する。

### 1.2. 設計原則

* **状態はフックで知る:** 状態は、AI CLI のフックが呼ぶ `tmac hook` で更新する。画面の文字列を読んで状態を判定しない。
* **常駐プロセスを持たない:** すべての処理は、コマンドの実行時（フックからの呼び出しを含む）に完結する。プロセスやペインの消失は、コマンドの実行時に確認して反映する（§3.5）。
* **状態はファイルで持つ:** エージェントの記録と状態は、データディレクトリ（§4）のファイルとして持ち、`ls` と `cat` で追えるようにする。データベースや索引ファイルは使わない。
* **迷ったら入力しない:** 入力できると確認できた場合だけ入力する（§1.4 の「入力できる」）。承認待ちの画面には入力しない。入力が受け付けられたか確認できないときは、再送せず、確認できるまで後続の入力も止める（§7.3）。誤った入力は取り消せないが、入力の遅れは後から取り戻せるためである。
* **速さより確実さ:** 放置して自動で進めることが目的であり、リアルタイム性は求めない。短い時間の競合は、数秒から 1 分程度待って避けてよい。待ち時間を短くするために、確実さを損なう手順は採らない。
* **人を優先する:** 人がペインで直接入力したことを検出したら、自動の入力を止める（§9.3）。
* **責務を広げない:** worktree、rules・skills の配置、Profile、メッセージ、ワークフローの制御は扱わない（§1.3）。呼び出し側が、それぞれの道具の CLI を組み合わせる。
* **組み合わせやすい出力:** 待つコマンドは、条件が成り立つか時間切れになるまでブロックし、結果を終了コードで返す（§14.4）。標準出力には、プログラムが読む結果だけを出す。

### 1.3. 扱う範囲

| 扱う | 扱わない（担当） |
| :--- | :--- |
| エージェントの起動・終了 | worktree の作成・削除（git、Dagu のワークフロー） |
| CLI へのフックの設定、フックによる状態の更新 | rules・skills の配置（rulesync） |
| 状態に応じた入力、入力の直列化、入力の確認 | Profile（起動コマンド・引数・権限・rulesync の target）の管理（呼び出し側） |
| 人の割り込みの検出と、入力の保留 | メッセージの保存・配送・通知（lmm） |
| フックの中継（`lmm hook` など）と、停止処理を起こす操作（§7.5） | タスクの順序、反復、完了の判定、人への質問と再開（Dagu、manager AI） |
| | 承認の確認（権限のプロンプト）への応答（人、または Profile の権限設定） |

* フックを持たない CLI には対応しない。
* 複数のマシンにまたがる運用は対象外とする。

### 1.4. 用語

| 用語 | 意味 |
| :--- | :--- |
| エージェント | tmac が起動し、1 つの tmux ペインで動く AI CLI。名前で識別する。 |
| プロジェクト | エージェントの所属。既定は、ディレクトリが属するリポジトリの名前（§3.1）。docker compose のプロジェクトにあたる。 |
| エージェント名 | プロジェクトの中でのエージェントの識別子（§3.1）。終了した後、同じ名前で起動し直せる。 |
| インスタンス ID | `spawn` ごとに発行する一意な ID（§3.1）。同じ名前で起動し直したエージェントと、以前のエージェントを区別する。 |
| 名札 | ペインに設定するペインオプション `@tmac_instance`（§4.4）。値はインスタンス ID。ペインを特定するために使う。 |
| ドライバ | CLI の種類ごとの扱い方。フックの設定、イベントと状態の対応、入力・終了の手順を定める。tmac に組み込む（§3.2）。 |
| 状態 | エージェントが入力を受け付けられるかどうか（§3.3）。 |
| 保留（hold） | tmac による入力を止める指定（§9）。状態とは独立している。 |
| 入力できる | 状態が `idle` になってから `send.settle_sec`（§12.2）以上たっており、有効な保留がないこと。 |
| 中継 | `tmac hook` が、受け取ったフックを別のコマンド（例: `lmm hook`）に渡すこと（§6.3）。 |
| 記録 | エージェントごとに持つディレクトリ（§4.2）。 |

## 2. 構成

```
 呼び出し側（人 / manager AI / Dagu のステップ）
   │  tmac spawn / send / wake / wait / status / hold / kill
   ▼
 tmac ──── tmux（new-window / paste-buffer / send-keys）────► ペイン: AI CLI
   │                                                              │ フック（SessionStart、Stop など）
   │ 読み書き                                                     ▼
 ~/.tmac/agents/<name>/ ◄────── 状態の更新 ────── tmac hook ──── 中継 ───► lmm hook など
```

### 2.1. 他のツールとの分担

| ツール | 担当 | tmac との接点 |
| :--- | :--- | :--- |
| lmm | メッセージの保存・配送・通知 | `spawn --env LMM_NAME=...` で自分のアドレスを渡す。`Stop` の中継で `lmm hook` を呼ぶ。送信者は `lmm post` の後に `tmac wake` を実行する（§13.1）。 |
| Dagu | 手順、分岐、反復、後片付け、人の回答待ち | ステップから tmac のコマンドを呼ぶ（§13.2）。Dagu のステップは端末を持たないため、対話型の CLI はステップの中で直接起動せず、tmac で tmux に起動する。 |
| git / rulesync | worktree の作成、rules・skills の配置 | tmac は関与しない。配置を終えたディレクトリを `--cwd` で受け取る。 |
| Profile（呼び出し側の設定） | AI CLI の起動コマンド・引数・権限、rulesync の target | tmac は Profile を読まない。起動コマンドと引数を、`spawn` の `--` の後で受け取る。 |
| tmux | ペインの表示、人の操作 | 人は `tmux attach` などで、ペインを直接見て操作できる。 |

* tmac は lmm と Dagu を前提にしない。lmm との接続は、中継コマンドの設定（§6.3）、環境変数（§5.4）、汎用の `tmac wake`（§7.5）だけで行い、tmac の内部に lmm 固有の処理を持たない。
* 他のツールの内部ファイルを読み書きしない。

## 3. エージェント

### 3.1. プロジェクト、エージェント名、インスタンス ID

* エージェントは、プロジェクトとエージェント名の組で識別する。コマンドでは `NAME`（プロジェクトを省略）か `PROJECT/NAME` で指定し、表示は `PROJECT/NAME` とする。
* プロジェクトは、docker compose のプロジェクトと同じく、次の順で決める。
    1. オプション `-p, --project <PROJECT>`（すべてのコマンドに共通）
    2. 環境変数 `TMAC_PROJECT`
    3. ディレクトリが属する Git リポジトリの名前。linked worktree（`git worktree`）の中では、メインのリポジトリのディレクトリ名（`git rev-parse --git-common-dir` の親）とする。Git の外では、ディレクトリ名とする。
    * 3 で使うディレクトリは、`spawn` ではエージェントの作業ディレクトリ（`--cwd`）、それ以外のコマンドではカレントディレクトリとする。エージェントは、作業するリポジトリのプロジェクトに属する。
    * 3 の名前は、英大文字を小文字にし、`a-z 0-9 . _ -` 以外の文字を `-` に置き換え、先頭の `a-z 0-9` 以外の文字を除いて、64 文字までにする。空になれば `default` とする。1・2 で指定した値は変換せず、規則に反すれば使い方の誤り（終了コード 2）とする。
* 複数のリポジトリで同じエージェント名（例: `coder`）を使っても衝突しない。リポジトリとその worktree の中では、短い名前で指定できる。
* プロジェクト名の規則は、エージェント名と同じとする。

* エージェント名に使用可能な文字は `a-z 0-9 . _ -` とし、先頭の文字は `a-z 0-9` のいずれかとする。長さは 1〜64 文字とする。
    * lmm のアドレス（lmm §3.1）と同じ規則である。同じ文字列を、エージェント名と `LMM_NAME` の両方に使えるようにするためである。ただし、両者の寿命は独立しており、tmac はメールボックスを作成・削除しない。
    * 名前はデータディレクトリのパスと tmux のウィンドウ名に使うため、`/` や `..` を含められないようにする。
* 同じプロジェクトに同じ名前の記録が存在する間は、その名前で起動できない（§5.3）。
* 名前を受け取るすべての箇所で規則を検証し、反する場合は使い方の誤り（終了コード 2）とする。`tmac hook` では終了コード 1 とする（§6.5）。
* インスタンス ID は、`spawn` が発行する UUID v4（小文字、ハイフン区切り）とする。記録（`agent.yml`）、ペインの名札（§4.4）、フックのコマンド（§5.5）に同じ値を持たせる。
    * 名前だけでは、終了したエージェントの遅れて届いたフックや、再利用された tmux のペイン ID を、同じ名前で起動し直したエージェントと区別できないためである。
* 名前を指定して実行するコマンド（`send`・`wake`・`wait`・`kill` など）は、開始した時点のインスタンス ID を対象とする。実行中に記録のインスタンス ID が変わった（同じ名前で起動し直された）場合は、対象のエージェントが終了したものとして扱う（終了コード 4）。

### 3.2. ドライバ

CLI の種類ごとの違いは、tmac に組み込んだドライバで吸収する。ドライバは次の項目を定める。

| 項目 | 内容 |
| :--- | :--- |
| フックの設定 | `tmac hook` を CLI に登録する方法（起動引数の追加、設定ファイルの生成など、§5.5） |
| ほかのフックの確認 | tmac 以外に、状態の判定を誤らせるフックが登録されていないかの確認（§5.6） |
| イベントと状態の対応 | どのフックのイベントで、どの状態に移すか（§3.4） |
| 入力の手順 | テキストの貼り付け方、送信のキー、貼り付けから送信までの間隔 |
| 入力の確認 | 入力が受け付けられたこと、または拒否されたことを、どのイベントで確認するか（§7.4） |
| 中継の結果の解釈 | 中継コマンドが停止や入力を止めたかどうかの判定（§6.3） |
| 終了の手順 | エージェントを正常に終了させる方法（§11） |

* ドライバの動作を YAML の手順で書き換える機能は設けない（旧仕様のアクションエンジンは廃止した）。CLI ごとの違いは、フックの入出力の形式や終了コードの意味など、キー操作の手順では表せない部分が大きいためである。調整が必要な値（貼り付けから送信までの間隔など）だけを、設定（§12）で変更できるようにする。

| ドライバ | CLI | 対応 | 備考 |
| :--- | :--- | :--- | :--- |
| `claude` | Claude Code | v0.1.0 | 基準とする。本書の対応表と手順は、このドライバについて定める。 |
| `codex` | Codex CLI | v0.1.0 | codex-cli 0.169.0 で確認した。対応表は §3.4、フックの設定は §5.5。 |
| `kiro` | Kiro CLI | 保留 | 対話型の TUI でフックが動かない不具合の報告がある。 |
| `agy` | Antigravity CLI | 保留 | 承認待ちなどのイベントがなく、フックの設定場所にも制約がある（同上）。 |

### 3.3. 状態

| 状態 | 意味 |
| :--- | :--- |
| `starting` | 起動した直後。CLI が、入力を受け付けられることをまだ知らせていない。 |
| `idle` | 入力待ち。 |
| `busy` | 処理中。 |
| `waiting` | 承認・確認の応答待ち（権限の確認など）。tmac は入力しない。 |
| `exited` | CLI が終了した、またはペインがなくなった。 |

* 状態は、CLI が入力を受け付けられるかを表す。タスクが完了したかは表さない。タスクの完了は、報告のメッセージ（lmm）で判定する（vision.md §7 の論点 2）。
* 保留（§9）は状態とは別に持つ。保留があっても、状態は `idle` のままとする。
* `exited` から別の状態へは移らない。

### 3.4. 状態の遷移（claude ドライバ）

| フックのイベント | 条件 | 遷移後の状態 | 中継との順序 |
| :--- | :--- | :--- | :--- |
| `SessionStart` | `source` が `startup`・`resume`・`clear` | `idle` | 中継の後 |
| `SessionStart` | `source` が `compact` | 変えない | — |
| `UserPromptSubmit` | — | `busy`。入力の照合（§7.4）と、人の入力の判定（§9.3）を行う | 中継の前 |
| `UserPromptSubmit` | 中継が入力を拒否した（§6.3） | `idle` | 中継の後 |
| `PreToolUse`・`PostToolUse`・`PostToolUseFailure` | — | `busy` | 中継の前 |
| `Notification` | 応答を求めるもの（`permission_prompt` など） | `waiting` | 中継の前 |
| `PermissionRequest` | — | `waiting` | 中継の前 |
| `Notification` | `idle_prompt` | `idle` | 中継の後 |
| `Notification` | 上記以外 | 変えない | — |
| `Stop` | — | 停止処理の通し番号（`stop_seq`、§4.2）を 1 増やす | 中継の前 |
| `Stop` | 中継が停止を止めなかった | `idle` | 中継の後 |
| `Stop` | 中継が停止を止めた（§6.3） | `busy` のまま | 中継の後 |
| `SessionEnd` | `reason` が `clear`・`resume` | 変えない（続く `SessionStart` を待つ） | — |
| `SessionEnd` | 上記以外 | `exited` | 中継の後 |

* `idle` へ移す更新は中継の後、`busy`・`waiting` へ移す更新は中継の前に行う。中継コマンドの実行中に、入力できると誤って判断しないためである。
* `stop_seq` は、中継を始める前に増やす。`tmac wake`（§7.5）が、ある時点より後に `Stop` の中継が始まったかを判定するために使う。
* `SessionStart` の `compact` で状態を変えないのは、作業の途中で自動の要約が起きた場合にも発火し、`idle` にすると処理中のエージェントに入力してしまうためである。
* `PreToolUse`・`PostToolUse` を使うのは、ユーザーの入力によらずに始まった処理（承認の後の再開など）を `busy` として捉えるためである。承認の後、ツールの実行が終わる（`PostToolUse`）までは `waiting` のまま見える。
* イベント名と値（`notification_type` など）は、実装時に採用した Claude Code の版で確認する（§15）。

#### codex ドライバ

| フックのイベント | 条件 | 遷移後の状態 | 中継との順序 |
| :--- | :--- | :--- | :--- |
| `SessionStart` | `source` が `resume`・`clear` | `idle` | 中継の後 |
| `SessionStart` | `source` が `startup` | 変えない | — |
| `UserPromptSubmit` | — | claude と同じ | 中継の前・後 |
| `PreToolUse`・`PostToolUse` | — | `busy` | 中継の前 |
| `PermissionRequest` | — | `waiting` | 中継の前 |
| `Stop` | — | claude と同じ | 中継の前・後 |
| `Interrupt` | — | `idle` | 中継の後 |
| `SessionEnd` | `reason` が `clear`・`resume` | 変えない | — |
| `SessionEnd` | 上記以外 | `exited` | 中継の後 |

* Codex は、起動しただけでは `SessionStart` を発火せず、最初の指示を受け取ったときに（`source: startup` で）発火する。そのため、`starting` から `idle` へは、最初の指示の `Stop` で移る。`spawn` には、起動コマンドの引数で最初の指示を渡す（§5.3）。渡さない場合は、`spawn` が時間切れ（終了コード 3）になる。
* Esc で中断すると、`Stop` ではなく `Interrupt` を発火するため、中断の後すぐに `idle` に戻る（claude の §3.5「中断」のような待ちはない）。
* 作業中に入力すると、Codex はそれを処理中のターンへの割り込みとして扱い、元の作業を中断して新しい入力に答える（codex-cli 0.169.0 で確認）。`idle` 以外では入力しない、という §1.4 の規則は、codex では特に重要である。
* `Interrupt`・`SessionEnd` のフックの時間の上限は、Codex が 3 秒に切り詰める。この 2 つのイベントに、時間のかかる中継は設定しない。

### 3.5. ペインの特定と、フックで捉えられない変化の補完

フックが発火しない変化は、tmac のコマンド（`status`・`list`・`wait`・`send`・`wake`・`kill`）の実行時に確認して反映する。

* **ペインの特定:** 名札（`@tmac_instance`）が記録のインスタンス ID と一致するペインを、そのエージェントのペインとする。`agent.yml` に保存したペイン ID は手がかりとして使い、使う前に名札を確認する。一致しなければ、tmux サーバーのすべてのペインから名札で探す。
    * tmux サーバーを再起動すると、同じペイン ID（`%0` など）が別のペインに使われる。保存した ID だけで操作すると、tmac の管理外のペインを操作してしまうためである。
* **プロセスとペインの消失:** 名札が一致するペインがない場合、またはそのペインのプロセスが終了している（`pane_dead`）場合は、`exited` にする。ペインのプロセスが終了していれば、その終了ステータスを記録する。
* **起動中の例外:** 状態が `starting` で、記録の作成から「起動を待つ時間（`agent.yml` に保存した `spawn` の `--timeout`）+ 60 秒」がたっていない間は、ペインが見つからなくても `exited` にしない。`spawn` は記録を作ってからペインを作る（§5.3）ため、その間に別のコマンドが確認しても、終了したと誤って判定しないためである。この時間を過ぎても見つからない場合は、`spawn` が途中で止まったものとみなし、`exited` にする。
* **中断:** Claude Code は、Esc で中断した場合に `Stop` を発火しないため、状態は `busy` のまま残る。`Notification` の `idle_prompt` を受け取った時点で `idle` に戻る。それまでの間、tmac は入力しない。
* `busy` が長く続く場合に、時間の経過だけで `idle` とみなすことはしない。待つ時間の上限は、呼び出し側が `--timeout` で決める。

## 4. データディレクトリ

### 4.1. 場所

* 環境変数 `TMAC_HOME` が設定されていればその値、なければ `~/.tmac` とする。
* `tmac spawn` は、解決した絶対パスを `TMAC_HOME` としてエージェントの環境に渡す（§5.4）。フックからも同じデータディレクトリを使うためである。
* データディレクトリは、`rename` と `flock(2)` が正しく動作するローカルファイルシステム上に置く。

### 4.2. 構成

```
~/.tmac/
├── config.yml                  # 設定（§12）
├── locks/
│   └── <project>/
│       ├── <name>.input.lock   # 入力と、入力を止める操作の直列化（§4.3）
│       └── <name>.state.lock   # 状態の読み書き（§4.3）
└── agents/
    ├── .creating/              # 作成途中の記録
    ├── .removing/              # 削除途中の記録
    └── <project>/              # プロジェクト（§3.1）。空になっても削除しない
        └── <name>/             # 記録
        ├── agent.yml           # 起動時に決まる情報（起動後は変更しない）
        ├── state.yml           # 現在の状態
        ├── holds/
        │   └── <key>.yml       # 保留。1 つの理由につき 1 ファイル（§9）
        ├── input.yml           # 処理中の入力（§7.3）
        ├── events.log          # フックと操作の記録
        └── driver/             # ドライバが生成した設定（例: claude-settings.json）
```

| ファイル | 内容 |
| :--- | :--- |
| `agent.yml` | 名前、インスタンス ID、ドライバ、作成日時、起動を待つ時間、作業ディレクトリ、起動したコマンドと引数（tmac が追加したものを含む）、渡した環境変数の名前、tmux のソケット・セッション・ペイン ID（手がかり）、中継の設定、人の入力による保留の時間 |
| `state.yml` | 状態、その状態になった日時（`since`）、更新の通し番号（`seq`）、停止処理の通し番号（`stop_seq`）、最後のイベントとその日時、終了ステータス（`exited` の場合） |
| `holds/<key>.yml` | 保留のキー、メモ、設定した日時。`unconfirmed` の保留は、確認できなかった入力のハッシュ値も持つ（§7.3） |
| `input.yml` | 入力の ID、テキストのハッシュ値（SHA-256）と長さ、入力した日時、進み具合（`pending`・`submitted`・`confirmed`・`rejected`） |
| `events.log` | 1 行に 1 件のテキスト。日時、通し番号、出どころ（`hook`・`send`・`wake`・`kill`・`check`）、イベント名、状態の変化 |

* 日時は UTC の RFC 3339 形式（マイクロ秒まで）とする。
* 環境変数の値は記録しない。秘密の値を含み得るためである。
* 入力したテキストそのものは記録しない。ハッシュ値と長さだけを記録する。

### 4.3. 書き込みとロック

* `state.yml`・`holds/`・`input.yml` は、同じディレクトリに一時ファイルを書いてから、`rename` で置き換える。読む側が、書きかけの内容を読まないようにするためである。
* ロックは `flock(2)` の排他ロックとし、次の 2 つを使う。

| ロック | 取得するもの | 保護するもの |
| :--- | :--- | :--- |
| 入力のロック（`<project>/<name>.input.lock`） | `send`・`wake` の入力、`hold`、`kill` | 入力の開始から確認までの区間。保留の設定と終了処理を、この区間と重ねない（§7.3、§9.2、§11） |
| 状態のロック（`<project>/<name>.state.lock`） | すべてのコマンドとフック | `state.yml`・`holds/`・`input.yml` の読み書き。短い時間だけ持ち、中継コマンドの実行中には持たない |

* 両方を取得する場合は、入力のロック、状態のロックの順に取得する。
* `tmac hook` は、入力のロックを取得しない。`tmac send` は入力のロックを持ったまま、フックによる入力の確認を待つため、フックが入力のロックを待つとデッドロックするためである。フックによる保留の操作（`human` の設定、`unconfirmed` の解除、§7.4・§9.3）は、状態のロックだけで行う。
* 記録の作成と削除は、lmm のメールボックス（lmm §9）と同じく、`.creating/`・`.removing/` で準備してから、上書きしない `rename` 1 回で切り替える。途中で停止しても、作りかけの記録が見えないようにするためである。
* ロックファイルは、記録を削除しても削除しない。削除されたロックファイルを待っていたプロセスと、新しく作られたロックファイルを取得したプロセスが、同時にロックを持たないようにするためである。

### 4.4. tmux のペインオプション

エージェントのペインに、次のペインオプションを設定する。

| オプション | 値 |
| :--- | :--- |
| `@tmac_instance` | インスタンス ID（名札）。ペインの特定に使う（§3.5）。 |
| `@tmac_agent` | エージェント名。表示用。 |
| `@tmac_state` | 状態。表示用。 |
| `@tmac_hold` | 有効な保留のキーをカンマで区切ったもの。保留がなければ空。表示用。 |

* `@tmac_instance` は、ペインの作成と同じ tmux の呼び出しで設定する（§5.3）。名札のないペインが、ほかのコマンドから見える時間を作らないためである。
* `pane-border-format` などで `#{@tmac_state}` を参照すると、各ペインに状態を表示できる。
* `@tmac_state`・`@tmac_hold` は表示用であり、正しい値は `state.yml`・`holds/` とする。状態や保留が変わったときだけ更新する。時間の経過で無効になった保留（§9.3）は、次に tmac のコマンドを実行したときに反映する。

## 5. 起動（`tmac spawn`）

### 5.1. コマンドインターフェース

```bash
tmac [-p <PROJECT>] spawn [OPTIONS] [<PROJECT>/]<NAME> -- <COMMAND> [ARGS]...
```

`COMMAND` と `ARGS` は、AI CLI の起動コマンドである（例: `claude --permission-mode acceptEdits`）。シェルを介さずに実行する。

### 5.2. オプション

| オプション | 説明 |
| :--- | :--- |
| `--driver <DRIVER>` | ドライバ。省略時は `COMMAND` のファイル名から決める（`claude` → `claude`、`codex` → `codex`）。決められない場合は、終了コード 2 とする。`env` や `mise exec --` などのラッパーを通す場合は、`--driver` を指定する。 |
| `-C, --cwd <DIR>` | 作業ディレクトリ。省略時はカレントディレクトリ。存在しない場合は、終了コード 2 とする。 |
| `-e, --env <KEY=VALUE>` | エージェントの環境変数を追加する。複数回指定できる。 |
| `--pass-env <KEY>` | 呼び出し元の環境変数 `KEY` の値を、エージェントに渡す。複数回指定できる。 |
| `--relay <EVENT=COMMAND>` | フックの中継（§6.3）。設定の `relay` より優先する。複数回指定できる。`COMMAND` を空にすると、そのイベントでは中継しない。 |
| `--session <SESSION>` | 新しいウィンドウを作る tmux セッション。省略時は設定の `tmux.session`、それもなければプロジェクト名（`.`・`:` は `-` に置き換える）。存在しなければ作成する。 |
| `--human-hold <SEC>` | 人の入力を検出した後に保留する時間（§9.3）。0 を指定すると、検出による保留をしない。省略時は設定の `hold.human_sec`。 |
| `--allow-foreign-hooks` | tmac 以外のフックが見つかっても起動する（§5.6）。 |
| `--timeout <SEC>` | 起動の完了（`idle`）を待つ時間の上限。省略時は設定の `spawn.timeout`。 |

* 既存のペインを分割して起動するオプション（旧案の `--split`）は、v0.1.0 では設けない。作成と同じ tmux の呼び出しで新しいペインに名札を付けるには、新しいペインを名前で指定する必要があり（§5.3）、分割したペインには名前を付けられないためである（§15）。

### 5.3. 実行フロー

1. **検証:** 名前（§3.1）、ドライバ、作業ディレクトリ、オプションを検証し、ほかのフックを確認する（§5.6）。同じ名前の記録が存在する場合は、終了コード 1 とする。`exited` の記録が残っている場合も同じとし、エラーメッセージで `tmac kill` を案内する。
2. **記録の作成:** インスタンス ID を発行する。`.creating/<name>/` に記録を作り、ドライバのフック設定（§5.5）を生成してから、`agents/<name>` へ `rename` する。状態は `starting` とする。
    * ペインを作る前に記録を作るのは、CLI が起動直後に呼ぶフックが、記録を見つけられるようにするためである。ペインがまだない間の扱いは §3.5 の「起動中の例外」に従う。
3. **ペインの作成と名札付け:** 次のコマンドを、1 回の tmux の呼び出し（`;` で区切ったコマンドの並び）で実行する。セッションが存在しない場合は、`new-window` の代わりに `new-session -d` で作る。
    1. `new-window -d -t <session>: -n <インスタンス ID> -c <cwd> -e ... -P -F '#{pane_id}' <COMMAND> [ARGS]...`
    2. `set-option -p -t =<session>:<インスタンス ID>` で、`@tmac_instance`・`@tmac_agent`・`remain-on-exit on` を設定する。
    3. `rename-window -t =<session>:<インスタンス ID> <NAME>`
    * 新しいペインは、一意なウィンドウ名（インスタンス ID）を完全一致（`=`）で指定する。対象を省略すると、`new-window -d` の後でも、元から選ばれていたペインに設定されるためである（tmux 3.7c で確認）。
    * 1 回の呼び出しの中のコマンドは、ほかのクライアントのコマンドに割り込まれずに実行される。tmux 3.7c で、作成と名札付けを 300 回繰り返す間に別のクライアントから一覧を取り続け、名札のない新しいペインが一度も見えないことを確認した（§15）。
    * 人が見ている画面は切り替えない（`-d`）。`remain-on-exit` により、CLI が異常終了しても、ペインと出力と終了ステータスを残す。
4. **記録の更新:** ペイン ID などを `agent.yml` に書き、表示用のペインオプション（§4.4）を設定する。
5. **起動の完了を待つ:** 状態が `idle` になるまで待つ。
    * `idle` になったら、`PROJECT/NAME PANE_ID` を 1 行出力して、終了コード 0 で終了する。
    * 先に CLI が終了した（`exited`）場合は、終了コード 1 とする。ペインと記録は調査のために残す。
    * 時間切れの場合は、終了コード 3 とする。エージェントは終了させずに残す。起動時の確認画面で止まっている場合などに、人がペインを見て判断できるようにするためである。

* 手順 3 が失敗した場合は、記録を削除して終了コード 1 とする。
* 片付けは、どの場合も `tmac kill`（§11）で行う。

### 5.4. 環境変数

エージェントのプロセスの環境変数は、tmux サーバーの環境に、次の変数を加えたものとする。

| 環境変数 | 値 |
| :--- | :--- |
| `TMAC_PROJECT` | プロジェクト |
| `TMAC_AGENT` | エージェント名 |
| `TMAC_INSTANCE` | インスタンス ID |
| `TMAC_HOME` | データディレクトリの絶対パス |
| `--env`・`--pass-env` で指定したもの | 指定した値 |

* tmux のペインは、tmac を呼び出したプロセスではなく、tmux サーバーの環境を受け継ぐ。呼び出し元の `PATH` などをエージェントに渡す場合は、`--pass-env` で明示する。
* 中継コマンド（`lmm hook` など）は、エージェントの環境で実行される（§6.4）。中継コマンドが使う `PATH` や `LMM_NAME` も、ここで渡す。

### 5.5. フックの設定（claude ドライバ）

* `driver/claude-settings.json` に、§3.4 のイベントで `tmac hook` を呼ぶフック設定を生成し、起動引数に `--settings <そのファイル>` を加える。worktree の中のファイルや、ユーザーの設定ファイルは変更しない。
* フックのコマンドには、tmac の実行ファイルの絶対パス、エージェント名、インスタンス ID を書く（例: `/usr/local/bin/tmac hook --project repo --agent impl-001 --instance 3f2a…-…9c claude Stop`）。エージェントの `PATH` に依存しないため、また、フックがそのたびに tmux へ問い合わせなくても、どの起動のフックかを判定できるようにするためである。
* `lmm hook` など、ほかのフック処理を同じイベントで動かす場合は、CLI の設定に直接登録せず、中継（§6.3）を使う。
* 呼び出し側の起動引数に `--settings`（ファイルのパスか JSON の文字列）がある場合は、その内容に tmac のフックを足したファイルを `driver/claude-settings.json` に作り、`--settings` をそのファイルに置き換える。権限などの設定を、tmac のフックと両立させるためである（§15 の 2）。
* tmac が加える引数は、`COMMAND [ARGS]...` のうち、ファイル名がドライバ名（`claude`）と一致する最初の引数の直後に入れる。見つからなければ `COMMAND` の直後に入れる。`env A=1 claude ...` のようなラッパーを通しても、CLI 自身の引数になるようにするためである。

### 5.5.1. フックの設定（codex ドライバ）

* §3.4 の codex ドライバのイベントで `tmac hook` を呼ぶフックを、起動引数の `-c hooks.<EVENT>=[{hooks=[{type="command",command="...",timeout=N}]}]` で加える。worktree の中の `.codex/hooks.json` や、ユーザーの設定ファイルは変更しない。引数を入れる位置は claude と同じ（ファイル名が `codex` の引数の直後）。
* フックのコマンドは `<tmac の絶対パス> hook codex <EVENT>` とし、エージェント名とインスタンス ID を含めない。フックは、エージェントの環境変数 `TMAC_AGENT`・`TMAC_INSTANCE`（§5.4）からエージェントを決める（§6.1）。
    * Codex は、フックを実行する前に、その定義（コマンドの文字列など）を人が確認して信頼することを求め、信頼を定義のハッシュ値で記録する（`~/.codex/config.toml` の `[hooks.state]`）。コマンドの文字列をエージェントごとに変えると、起動のたびに確認の画面で止まるためである。同じ tmac の実行ファイルを使う限り、最初の 1 回だけ確認すればよい。
    * tmac は、確認を省く `--dangerously-bypass-hook-trust` を加えない。信頼の判断は利用者に残す。確認の画面で止まった場合、`spawn` は時間切れ（終了コード 3）になるため、人がペインで確認してから `tmac wait` で待つ。
* 新しいリポジトリでは、Codex がフォルダーの信頼も確認する。信頼したリポジトリの worktree では確認されない（codex-cli 0.169.0 で確認）。

### 5.6. ほかのフックの確認（claude ドライバ）

状態の判定は、`Stop` と `UserPromptSubmit` で、停止や入力を止め得るフックが tmac だけであることを前提にする（§6.3）。Claude Code は、ユーザー・プロジェクト・ローカル・管理者の設定と、有効なプラグインのフックを合成して実行する。`--settings` で tmac のフックを加えても、それらのフックは残る。

* `spawn` は、読める範囲の設定（`~/.claude/settings.json`、作業ディレクトリの `.claude/settings.json`・`.claude/settings.local.json`、管理者の設定ファイル）と、有効なプラグインのフック定義を調べる。`Stop`・`UserPromptSubmit` に tmac 以外のフックがあれば、見つけた場所を標準エラー出力に示し、起動せずに終了コード 2 とする。
    * そのフックが停止や入力を止めるかどうかは、実行してみるまで分からないためである。
* 通知やログだけを行い、停止や入力を止めないと分かっているフックの場合は、`--allow-foreign-hooks` で起動できる。いつも同じ場所にあるもの（利用者が入れたプラグインなど）は、設定の `spawn.allow_foreign_hooks`（§12.2）に書いておけば、`--allow-foreign-hooks` なしで起動できる。止める可能性のある処理は、CLI の設定から外して中継（§6.3）に移す。
* 設定の読み込み元（`--setting-sources`）は制限しない。権限や rules などの必要な設定まで読まれなくなるためである。
* 見落としたフックが停止を止めた場合に備え、入力の前に、`idle` が `send.settle_sec` 続くことを確かめる（§1.4「入力できる」）。止められた後の処理でツールを使えば、`PreToolUse` で `busy` に戻るため、多くの場合はこの間に気付ける。
* 呼び出し側の `--settings`（§5.5）にある `Stop`・`UserPromptSubmit` のフックも、tmac 以外のフックとして扱う。
* codex ドライバでは、`/etc/codex/`、`$CODEX_HOME`（既定 `~/.codex`）、プロジェクトのルートから作業ディレクトリまでの各 `.codex/` の `hooks.json` と `config.toml`（`[hooks]`）、呼び出し側の起動引数の `-c hooks.*` を調べる。

## 6. フック（`tmac hook`）

### 6.1. コマンドインターフェース

```bash
tmac hook [--project <PROJECT>] [--agent <NAME>] [--instance <ID>] <DRIVER> <EVENT>
```

ドライバが CLI に登録するコマンドであり、人が直接実行することは想定しない。フックの入力（JSON）を標準入力から読む。`--project`・`--agent`・`--instance` を省略した場合は、環境変数 `TMAC_PROJECT`・`TMAC_AGENT`・`TMAC_INSTANCE` を使う（プロジェクトは §3.1 の 3 では決めない）。

### 6.2. 実行フロー

1. エージェント名かインスタンス ID が決まらない場合は、何もせずに終了コード 0 で終了する。記録が存在しない場合、または記録のインスタンス ID がフックのインスタンス ID と一致しない場合は、警告を出力し、中継もせずに終了コード 0 で終了する。
    * `tmac kill` の後や、同じ名前で起動し直した後に、以前の CLI が終了処理中にフックを呼ぶことがあるためである。以前のフックで、新しいエージェントの状態を変えたり、中継を実行したりしない。
2. 標準入力をすべて読む。
3. 状態のロックを取得してインスタンス ID をもう一度確認し、§3.4 で「中継の前」とした更新を行う。`UserPromptSubmit` では、入力の照合（§7.4）と人の入力の判定（§9.3）もここで行う。ロックを解放する。
4. 中継コマンドがあれば実行する（§6.3）。
5. 状態のロックを取得してインスタンス ID をもう一度確認し、§3.4 で「中継の後」とした更新を行う。`UserPromptSubmit` では、入力の確認結果（§7.4）もここで確定する。中継の間に記録が削除されたり置き換えられたりしていれば、何も更新しない。
6. `events.log` に記録する。状態か保留が変わった場合は、ペインオプション（§4.4）を更新する。

### 6.3. 中継

CLI の 1 つのイベントに複数のフックを登録すると、CLI はそれらを並列に実行し、結果を合成する（Claude Code では、停止を止める判定が 1 つでもあれば停止しない）。そのため、tmac のフックからは、ほかのフック（例: `lmm hook`）が停止を止めたかどうかが分からない。`lmm hook` が `Stop` で停止を止めてエージェントが新着メッセージの処理を続けていても、tmac は `idle` と判断して入力してしまう。

これを防ぐため、CLI に登録するフックは tmac だけとし（§5.6）、ほかのフック処理は tmac が中継する。

* **中継コマンド:** イベントごとに 1 つのシェルコマンド文字列とする。複数の処理が必要な場合は、スクリプトにまとめる。`spawn --relay`、設定の `relay.<driver>.<event>` の順で決め、`agent.yml` に保存する。
* **実行:** `/bin/sh -c <コマンド>` で実行する。カレントディレクトリは `tmac hook` のカレントディレクトリ、標準入力は §6.2 の手順 2 で読んだ内容とする。標準出力・標準エラー出力は `tmac hook` のものをそのまま使い、中継コマンドの終了コードを `tmac hook` の終了コードとする。`lmm hook` の通知コマンド（lmm §8.4）と同じ方式である。
* **時間の上限:** 設定の `relay.timeout` を超えた場合は、プロセスグループ全体に `SIGTERM` を送り、2 秒たっても終了しなければ `SIGKILL` を送る。その後、エラーを出力して終了コード 1 とする。`relay.timeout` は、CLI 自身のフックの時間の上限（Claude Code の `UserPromptSubmit` は 30 秒）より短くする。
* **止めたかどうかの判定（claude）:** `Stop`・`UserPromptSubmit` の中継コマンドが、終了コード 2 で終了した場合、または終了コード 0 で、`"decision": "block"` を含む JSON オブジェクトを標準出力に出した場合に、止めたと判定する。`Stop` では停止を止めた（処理を続ける）ことを、`UserPromptSubmit` では入力を拒否した（CLI は入力を処理せずに捨てる）ことを表す。
* **保留との関係:** 保留（§9）中も中継する。保留は tmac による入力を止めるものであり、CLI 自身の動作は変えないためである（§15）。

中継の用途の例:

| イベント | 中継コマンドの例 | 用途 |
| :--- | :--- | :--- |
| `Stop` | `lmm hook` | 停止のたびに新着メッセージを渡す（§13.1） |
| `Notification` | 承認待ちを人に知らせるスクリプト | 人の応答が必要なことを、デスクトップ通知などで知らせる |

### 6.4. 中継コマンドの環境変数

中継コマンドには、`tmac hook` の環境変数（CLI から受け継いだもの。`TMAC_AGENT`、`LMM_NAME` などを含む）に、次の変数を加えて渡す。

| 環境変数 | 値 |
| :--- | :--- |
| `TMAC_EVENT` | イベント名（例: `Stop`） |

### 6.5. 終了コード

* 中継コマンドを実行した場合は、その終了コードを返す。
* それ以外の場合は 0 か 1 だけを返し、2 を返さない。Claude Code の `Stop` フックでは、終了コード 2 が「停止させずに続ける」ことを表すため、tmac 自身のエラーで 2 を返すと、エージェントが止まれなくなるためである（lmm §8.3 と同じ理由）。
* 状態の更新に失敗しても、中継コマンドは実行する。メッセージの通知などを、tmac の状態の不具合で止めないためである。ただし、§6.2 の手順 1 で以前の起動のフックと判定した場合は、中継しない。

## 7. 入力（`tmac send` / `tmac wake`）

### 7.1. コマンドインターフェース

```bash
tmac send [OPTIONS] <NAME> [TEXT]
```

`TEXT` を省略した場合は、標準入力から読む。

| オプション | 説明 |
| :--- | :--- |
| `-f, --file <PATH>` | ファイルの内容を入力する。`TEXT` とは同時に指定できない。 |
| `--timeout <SEC>` | 入力できる状態になるまで待つ時間の上限。省略時は上限なし。 |
| `--no-wait` | 入力できない場合は、待たずに終了コード 5 で終了する。 |

### 7.2. 入力するテキスト

* UTF-8 で、改行（LF）とタブ以外の制御文字を含まないものとする。反する場合は、終了コード 2 とする。
    * エスケープ（`ESC`）を許すと、貼り付けの終わりを表す制御シーケンスを送れてしまい、テキストの一部がキー操作として解釈されるためである。
* 長さは、設定の `send.max_bytes` 以下とする。空のテキストはエラーとする。
* 末尾の改行は取り除く。送信のキーは tmac が送るためである。
* 長い依頼は、本文をファイル（lmm のメッセージなど）に置き、そのことを伝える短いテキストを送ることを推奨する。

### 7.3. 実行フロー

1. **入力できるまで待つ:** 0.5 秒ごとに状態を確認し（§3.5 の確認を含む）、入力できる（§1.4）まで待つ。`exited` の場合、記録がない場合、インスタンス ID が変わった場合は終了コード 4、時間切れは終了コード 3 とする。
2. **入力のロック:** 入力のロックを取得し、入力できることをもう一度確認する。入力できなければ、ロックを解放して手順 1 に戻る（`--no-wait` では終了コード 5）。
    * `input.yml` が残っている場合は、以前の入力が手順 3〜5 の途中で止まった（プロセスが強制終了されたなど）とみなす。`confirmed`・`rejected` なら削除して続ける。それ以外なら、その入力を `unconfirmed` の保留に移し（手順 5 と同じ）、ロックを解放して手順 1 に戻る。
3. **入力の記録:** `input.yml` に、入力の ID、テキストのハッシュ値、進み具合 `pending` を書く。
4. **貼り付けと送信:** 次の順で入力する。
    1. テキストを、この入力専用の名前付きバッファ（`tmac-<インスタンス ID>-<入力の ID>`）に読み込む（`load-buffer -b <名前> -`）。
    2. 名札（§3.5）が一致することを確認したうえで、そのペインにブラケットペーストで貼り付け、バッファを削除する（`paste-buffer -p -d -b <名前> -t <ペイン>`）。確認と貼り付けは、1 回の tmux の呼び出しで行う（§11 の手順 6 と同じ方法）。
    3. ドライバの間隔だけ待ってから、同じく名札を確認して送信のキー（`Enter`）を送る。
    * バッファの名前を必ず指定するのは、tmux のバッファがサーバー全体で共有され、名前を省くと直近に読み込まれたバッファが使われるためである。別のエージェントへの入力が並行すると、ほかの依頼を貼り付けてしまう（tmux 3.7c で確認）。名前付きバッファは、人が使う貼り付けのバッファにも影響しない。
    * テキストは、コマンドの引数ではなく標準入力で tmux に渡す。シェルや tmux のコマンドとして解釈させないためである。
    * `if-shell -F` は、名札が一致しなくても成功で終わる。そのため、一致しなかった場合に分かる出力を返させ（else 側で `display-message -p` を使うなど）、貼り付けたかどうかを tmac が判別できるようにする。貼り付ける前に一致しなかった場合は、バッファと `input.yml` を削除して終了コード 4 とする（ペインがなくなったとみなす）。
    * 読み込みや貼り付けに失敗した場合は、バッファを削除する（`delete-buffer -b <名前>`）。貼り付けた後に送信のキーを送れなかった場合は、入力欄にテキストが残っているおそれがあるため、手順 5 の「確認できなかった」と同じに扱う。
    * 貼り付けから送信のキーまでの間は、`SIGINT`・`SIGTERM` を受け取っても中断せず、送信のキーを送ってから終了する。テキストだけが入力欄に残り、次の入力と連結されるのを防ぐためである。
5. **入力の確認:** `input.yml` の進み具合が `confirmed` か `rejected` になる（§7.4）のを、設定の `send.confirm_timeout` まで待つ。
    * `confirmed`: `input.yml` を削除し、ロックを解放して終了コード 0 で終了する。
    * `rejected`: 中継が入力を拒否し、CLI は入力を捨てた。入力欄は空になっているため、保留はしない。`input.yml` を削除し、ロックを解放して終了コード 7 で終了する。
    * 時間切れ: ロックを解放する前に、`input.yml` の内容（ハッシュ値を含む）を `holds/unconfirmed.yml` の保留に移し、終了コード 6 で終了する。再送はしない。
        * 入力されたかどうかが分からないうえ、入力欄にテキストが残っている（送信のキーが改行として扱われた場合など）おそれがあるためである。保留にしないと、待っていた次の入力が貼り付けられ、2 つの依頼が連結される。
        * `unconfirmed` の保留は、後から `UserPromptSubmit` が届いたときに自動で解除する（§7.4）。入力欄の内容は送信されると空になるためである。届かない場合は、人がペインを確認して `tmac release --key unconfirmed` で解除する。

* 複数の `tmac send` を同時に実行した場合は、手順 2 のロックで 1 件ずつ処理する。順序は保証しない。
* 待っている間（手順 1、2）に `SIGINT`・`SIGTERM` を受け取った場合は、何も入力せずに、終了コード 128 + シグナル番号で終了する。

### 7.4. 入力の照合と確認（claude ドライバ）

`UserPromptSubmit` のフックは、次のように入力を照合し、中継の結果を見てから確認結果を確定する。

* **中継の前（§6.2 の手順 3）:**
    * `unconfirmed` の保留があれば解除する。入力の `prompt` がその保留のハッシュ値と一致すれば、確認できなかった tmac の入力が遅れて届いたものとし、以下では tmac の入力として扱う。
    * `input.yml` が `pending` で、`prompt` とハッシュ値が一致すれば（改行コードと前後の空白を正規化して比べる）、進み具合を `submitted` にする。
    * どちらにも一致しなければ、人の入力とみなす（§9.3）。
    * 状態を `busy` にする。
* **中継の後（§6.2 の手順 5）:**
    * 中継が入力を拒否した（§6.3）場合は、状態を `idle` に戻し、`submitted` の入力を `rejected` にする。
    * それ以外の場合は、`submitted` の入力を `confirmed` にする。
* `tmac send` が成功（終了コード 0）を返すのは、`confirmed` になった後、つまり CLI が入力を受け付けて処理を始めた後に限る。

### 7.5. 停止処理を起こす（`tmac wake`）

```bash
tmac wake [--timeout <SEC>] <NAME> [TEXT]
```

コマンドを実行した時点より後に、エージェントの `Stop` フック（とその中継）が少なくとも 1 回始まるようにする。`lmm post` の後に実行すると、配送したメッセージが必ず `lmm hook` に渡る（§13.1）。`TEXT` の扱いは `tmac send` と同じ（§7.2）。

1. 実行した時点の `stop_seq`（§4.2）を読む。
2. 0.5 秒ごとに、次を上から順に確認する。
    * `stop_seq` が増えた（実行の後に `Stop` フックが始まった）: 何も入力せずに、終了コード 0 で終了する。
    * `exited`、記録がない、インスタンス ID が変わった: 終了コード 4 で終了する。
    * 入力できる（§1.4）: `TEXT` を §7.3 の手順 2〜5 で入力し、その結果の終了コードで終了する。エージェントは `TEXT` の処理を終えて停止するときに、`Stop` フックを始める。
3. `--timeout` を過ぎたら、終了コード 3 で終了する。省略時は上限なし。

* `Stop` フックが「新着なし」と判断した直後に配送されたメッセージは、宛先がそのまま `idle` になると、次の入力まで誰にも渡されない。配送後に一度だけ `send --no-wait` を試す方法では、この間に「入力できない」と断られて取りこぼす。`wake` は、配送の後に始まった `Stop` を確認するか、入力できるようになって知らせを入力するまで待つことで、取りこぼしをなくす。
    * `stop_seq` は `Stop` フックが中継を始める前に増やす（§3.4）。そのため、`wake` の実行より後に増えたなら、その中継は配送の後に始まっており、メッセージを受け取れる。
* 処理中・承認待ちの宛先には入力しない。保留中は、`Stop` が始まるか、保留が解除されるまで待つ。人の入力による保留（§9.3）が時間で無効になった場合も、入力できるようになった時点で知らせを入力する。
* 呼び出し側は、宛先が停止するまで待つことになる。待てない呼び出し側（シェルのツールから呼ぶエージェントなど）は、バックグラウンドで実行する。

## 8. 待機（`tmac wait`）

```bash
tmac wait [--state <STATE>[,<STATE>...]] [--timeout <SEC>] <NAME>
```

状態が、指定したもののいずれかになるまで待つ。`--state` の省略時は `idle` とする。

* 0.5 秒ごとに状態を確認する（§3.5 の確認を含む）。
* 一致したら、その状態を 1 行出力して、終了コード 0 で終了する。
* 指定に `exited` を含まないのに `exited` になった場合、記録がない場合、インスタンス ID が変わった場合は、終了コード 4 とする。
* 時間切れは終了コード 3、シグナルによる中断は 128 + シグナル番号とする。
* `idle` は、依頼が完了したことを意味しない（§3.3）。依頼の完了は、報告のメッセージを `lmm wait` で待つ。

## 9. 保留（`tmac hold` / `tmac release`）

### 9.1. コマンドインターフェース

```bash
tmac hold [--key <KEY>] [--note <TEXT>] [--timeout <SEC>] <NAME>
tmac release [--key <KEY> | --all] <NAME>
```

* `--key`: 保留の理由を表す識別子。省略時は `manual` とする。文字の規則はエージェント名（§3.1）と同じ。
* tmac が使う次のキーは予約とし、`hold` には指定できない（`release` には指定できる）。

| キー | 設定するもの | 解除 |
| :--- | :--- | :--- |
| `human` | 人の入力の検出（§9.3） | 時間の経過、または `release` |
| `unconfirmed` | 入力を確認できなかった `send`・`wake`（§7.3） | 後から届いた `UserPromptSubmit`（§7.4）、または `release` |

* 同じキーの保留がすでにある場合は、メモを置き換えて成功とする。存在しないキーの `release` は、警告を出力して成功とする。
* 記録がない場合は、終了コード 4 とする。
* `hold` は入力のロックを取得してから保留を書き込む（§9.2）。`--timeout` はロックを待つ時間の上限で、省略時は `send.confirm_timeout` + 60 秒とする。時間切れは終了コード 3 とする。

### 9.2. 保留の効果

* 有効な保留が 1 つでもある間、`tmac send`・`tmac wake` は入力しない（待つか、`send --no-wait` では終了コード 5 で終了する）。
* `tmac hold` が成功した時点で、tmac による入力は、実行中のものも含めて終わっている。`hold` は入力のロックを取得して、実行中の入力（貼り付けから確認まで）が終わるのを待ってから、保留を書き込むためである。人は `hold` の成功を確認してから、ペインで直接入力を始めてよい。
* `tmac kill` は、入力のロックを取得した後に保留を確認し、`--force` がない限り終了コード 5 で終了する（§11）。人が操作している、または人の確認を待っているエージェントを、ワークフローの後片付けで終了させないためである。
* 保留は、CLI の動作とフックの中継を止めない（§6.3）。
* 保留はキーごとに独立している。あるキーの解除は、ほかのキーに影響しない。例えば、ワークフローが人の回答待ちに設定した保留（`--key q-123`）は、人の入力の検出による保留（`human`）が時間で無効になっても残る。

### 9.3. 人の入力の検出

`UserPromptSubmit` のフックで、tmac が入力していないテキストの送信を受け取った場合（§7.4）は、人がペインで直接入力したとみなし、`holds/human.yml` を作成（または更新）する。

* フックは、この保留を状態のロックだけで書き込み、入力のロックは取得しない（§4.3）。
* `human` の保留は、エージェントが `idle` になってから `--human-hold` の秒数が過ぎると無効になる。人が続けて入力すると、そのたびに更新される。
    * 有効かどうかは、`state.yml` の `since` と保留の日時から、コマンドの実行時に判定する。常駐プロセスで時間を計る必要はない。
* `--human-hold 0` で起動したエージェントでは、検出による保留をしない。人と常に対話する manager AI などで使う。
* 状態が `starting` の間に届いた入力は、人の入力とみなさない。起動コマンドの引数で渡した最初の指示（codex ドライバ、§3.4）が、これにあたる。
* CLI が自分で作る入力も、人の入力とみなさない。Claude Code は、バックグラウンドのコマンドが終わった知らせ（`<task-notification>` で始まる）を入力として渡し、そのときも `UserPromptSubmit` を発火させる（claude ドライバ。Claude Code 2.1.325 で確認）。
* 無効になった `human` の保留は、状態のロックを持つ処理（入力、`kill`、フック）が見つけた時点で削除する。残しておくと、次に `idle` になったときの `since` から数え直され、保留が復活するためである。
* 人が入力欄に書きかけで、まだ送信していないテキストは検出できない（§15）。人は、直接入力する前に `tmac hold` を実行し、その成功を確認してから入力することを推奨する。

## 10. 状態の表示（`tmac status` / `tmac list`）

```bash
tmac status [--field <KEY>] [<PROJECT>/]<NAME>
tmac list [-q] [-a]
```

`status` は、§3.5 の確認を行ってから、エージェントの情報を YAML で出力する。記録がない場合は、終了コード 4 とする。

```yaml
project: repo
name: impl-001
instance: 3f2a6c1e-8b7d-4e2f-9a1b-5c6d7e8f9a0b
driver: claude
state: idle
since: 2026-10-12T05:01:02.345678Z
holds: []
cwd: /home/dev/worktrees/impl-001
tmux:
  session: repo
  window: impl-001
  pane: "%12"
pid: 12345
created_at: 2026-10-12T05:00:40.123456Z
```

* `pid` は、名札を確認したペインのプロセス ID（`#{pane_pid}`）を、その時点で取得したものとする。
* `--field <KEY>`: 1 つの値だけを出力する（例: `--field state`）。文字列以外の値（`holds` など）は、JSON で 1 行に出力する。
* `list` は、プロジェクト（§3.1）のエージェントを表で出力する。`-a` を指定すると、すべてのプロジェクトのエージェントを出力する（docker compose の `ps` と `docker ps` の関係にあたる）。列は、`PROJECT/NAME`、ドライバ、状態、その状態の経過時間、保留、ペイン、作業ディレクトリとする。`-q` を指定すると、`PROJECT/NAME` だけを 1 行に 1 つ出力する。

## 11. 終了（`tmac kill`）

```bash
tmac kill [--timeout <SEC>] [--force] <NAME>
```

エージェントを終了させ、ペインと記録を削除する。CLI がすでに終了している（`exited`）場合は、ペインと記録の削除だけを行う。

1. 記録がなければ、終了コード 4 とする。
2. 入力のロックを取得する（実行中の入力の終了を待つ）。
3. 状態のロックを取得して、保留を確認する。有効な保留があり、`--force` がなければ、ロックを解放して終了コード 5 とする。
    * 入力のロックを取得した後に確認するのは、ロックを待っている間に設定された保留を見落とさないためである。入力のロックを持っている間は、`hold` は保留を書き込めない（§9.2）。
4. 名札でペインを特定する（§3.5）。名札が一致するペインがなければ、tmux には何もせずに手順 7 へ進む。
    * サーバーの再起動などで、保存したペイン ID が別のペインを指している場合に、そのペインを閉じないためである。
5. CLI がまだ動いていれば、ドライバの終了の手順を行う。`--force` では、この手順を省く。
    * claude: `idle` なら、§7.3 の手順 3、4 と同じ方法で `/exit` を入力する。それ以外の状態では、CLI のプロセスに `SIGTERM` を送る。承認の確認の画面などに、`/exit` を入力しないためである。
    * codex: claude と同じで、入力するのは `/quit` とする。
    * シグナルを送るプロセスは、保存したプロセス ID ではなく、名札を確認したペインからその時点で取得したプロセス ID（`#{pane_pid}`）とする。取得した ID のプロセスの開始時刻も記録し、以後のシグナルは、同じ ID で開始時刻も一致するプロセスにだけ送る。プロセス ID が別のプロセスに再利用されている場合に、誤って送らないためである。
6. `--timeout`（省略時は設定の `kill.timeout`）まで、CLI の終了を待つ。終了しなければ、ペインを閉じる。ペインを閉じた 2 秒後に、手順 5 で記録したプロセスが残っていれば、そのプロセスグループに `SIGKILL` を送る。
    * ペインを閉じるときは、名札の確認と `kill-pane` を 1 回の tmux の呼び出しで行う（例: `if-shell -F -t <ペイン> '#{==:#{@tmac_instance},<ID>}' 'kill-pane -t <ペイン>'`）。確認と操作の間に、ペインが入れ替わらないようにするためである。`--force` でも、この確認は省かない。
7. 名札が一致するペインが残っていれば、手順 6 と同じ方法で閉じる。記録を `.removing/` へ移して削除し、ロックを解放する。

* worktree、ブランチ、メールボックスには触れない。それらは呼び出し側が片付ける。
* 作業途中の内容は保証しない。成果の保存（commit など）は、終了させる前に呼び出し側が確認する。

## 12. 設定

### 12.1. 設定ファイル

* `$TMAC_CONFIG`、未設定なら `$TMAC_HOME/config.yml`（`~/.tmac/config.yml`）とする。`TMAC_CONFIG` で指定したファイルが存在しない場合はエラーとし、既定の場所に存在しない場合は、設定なしとして扱う。
* 形式は YAML とし、すべての項目を省略できる。未知のキーは、警告を出力して無視する。
* 値は、コマンドラインのオプション、設定ファイル、組み込みの既定値の順で決める（前が優先）。
* lmm のような、ディレクトリごとの階層型の設定は設けない。tmac はワークフローなどから任意のカレントディレクトリで呼ばれ、エージェントごとの違いは `spawn` のオプションで渡すためである。

### 12.2. 設定項目

| キー | 型 | 組み込みの既定値 | 説明 |
| :--- | :--- | :--- | :--- |
| `tmux.session` | string | なし（プロジェクト名） | `spawn` が新しいウィンドウを作るセッション。省略すると、プロジェクトごとのセッション（プロジェクト名の `.`・`:` を `-` に置き換えた名前）にする。 |
| `tmux.socket_name` | string | なし（tmux の既定） | tmux の `-L` に渡すソケット名。`spawn` で使ったソケットを `agent.yml` に記録し、以後のコマンドはそのソケットを使う。 |
| `spawn.timeout` | 数値（秒） | `60` | 起動の完了を待つ時間の上限。 |
| `spawn.allow_foreign_hooks` | 真偽値、または文字列のリスト | `false` | tmac 以外のフックがあっても起動を断らない範囲（§5.6）。`true` はすべて、リストは、`spawn` が示す場所（例: `plugin codex@openai-codex (...)`）がいずれかの文字列で始まるものを許す。 |
| `send.settle_sec` | 数値（秒） | `10` | 入力できるとみなすまでに、`idle` が続く必要がある時間（§1.4）。リアルタイム性は求めないため、長めにしてよい。 |
| `send.confirm_timeout` | 数値（秒） | `15` | 入力の確認を待つ時間の上限。 |
| `send.max_bytes` | 整数 | `65536` | 入力するテキストの長さの上限。 |
| `kill.timeout` | 数値（秒） | `30` | 終了を待つ時間の上限。 |
| `hold.human_sec` | 数値（秒） | `300` | 人の入力による保留の時間（§9.3）。 |
| `relay.timeout` | 数値（秒） | `20` | 中継コマンドの実行時間の上限（§6.3）。 |
| `relay.<driver>.<event>` | string | なし | 中継コマンド（§6.3）。 |
| `drivers.claude.submit_delay_ms` | 整数（ミリ秒） | `200` | 貼り付けから送信のキーまでの間隔。 |
| `drivers.codex.submit_delay_ms` | 整数（ミリ秒） | `500` | 同上（codex ドライバ）。 |

例:

```yaml
tmux:
  session: agents
relay:
  claude:
    Stop: lmm hook
send:
  settle_sec: 30
hold:
  human_sec: 600
```

| :--- | :--- |

## 13. 使い方の例

### 13.1. lmm との接続

lmm のメッセージは、エージェントが停止するたびに、`Stop` フックの `lmm hook` で受け取る（lmm §8、§11）。tmac で起動するエージェントでは、`lmm hook` を CLI の設定に直接登録せず、中継として設定する（§6.3）。

```yaml
# ~/.tmac/config.yml
relay:
  claude:
    Stop: lmm hook
```

```yaml
# ~/.lmm/config.yml（lmm §10.6 の例と同じく、Stop フック用の JSON を出力させる）
hook:
  cmd: >-
    jq -n --arg paths "$LMM_RECEIVED"
    '{decision: "block", reason: ("新着メッセージがあります。次のディレクトリの index.md を読んで対応し、処理後に削除してください:\n" + $paths)}'
```

```bash
lmm box create impl-001 --exist-ok
tmac spawn impl-001 --cwd "$WT" --env LMM_NAME=impl-001 --pass-env PATH -- claude
```

送信者は、`lmm post` が成功した後に `tmac wake`（§7.5）を実行する。

```bash
lmm post -t impl-001 -s "実装依頼" ./request
tmac wake impl-001 "新着メッセージがあります。"
```

| `wake` を実行したときの宛先 | 届き方 |
| :--- | :--- |
| `busy`・`waiting` | 処理を終えて停止するときに、`Stop` の中継で受け取る。`wake` は `Stop` が始まったことを確認し、何も入力せずに終了する。 |
| `idle` | `wake` が知らせを入力する。エージェントは、知らせの処理を終えて停止するときに、`Stop` の中継でメッセージを受け取る。 |
| `starting` | 起動が終わり、入力できるようになってから、`wake` が知らせを入力する。 |
| 保留中 | `wake` は、`Stop` が始まるか、保留が解除されて入力できるようになるまで待つ。 |

* `wake` は必ず `lmm post` の成功の後に実行する。順序が逆だと、`wake` が確認した `Stop` の中継が、配送より前に新着を調べ終えている場合がある。
* tmac にメッセージのキューは持たせない。メッセージは lmm の受信箱に残り、`wake` は「配送の後に `Stop` の中継が 1 回走ること」だけを保証する。
* `UserPromptSubmit` に `lmm hook` を中継する場合は、上の `hook.cmd`（`decision: "block"`）を使わないこと。`UserPromptSubmit` で `block` を返すと、入力そのものが拒否される（§6.3）。

### 13.2. Dagu から使う

以下は、実装タスクのワークフローの構成例である（worktree の準備は済んでいるものとする）。Dagu 上での動作は未確認である。

```yaml
name: implement
type: chain
shell: bash

params:
  - TASK: ""          # タスク実行 ID。エージェント名とアドレスに使う
  - WT: ""            # 準備済みの worktree
  - REQUEST_DIR: ""   # 依頼のメッセージディレクトリ

env:
  - FLOW: flow-${TASK}   # ワークフロー側のアドレス

steps:
  - id: mailbox
    run: lmm box create ${TASK} --exist-ok && lmm box create ${FLOW} --exist-ok

  - id: spawn
    run: >-
      tmac spawn ${TASK} --cwd ${WT}
      --env LMM_NAME=${TASK} --pass-env PATH
      -- claude --permission-mode acceptEdits

  - id: request
    run: |
      set -euo pipefail
      LMM_NAME=${FLOW} lmm post -t ${TASK} -s "実装依頼" ${REQUEST_DIR} | cut -d' ' -f1
    output: REQUEST_ID

  - id: notify
    # 宛先が停止処理を 1 回通るまで待つ。宛先が作業中なら、その作業が終わるまで待つ
    run: tmac wake --timeout 3600 ${TASK} "新着メッセージがあります。"

  - id: report
    # 報告は lmm post --reply で返してもらい、依頼への返信だけを待つ
    run: LMM_NAME=${FLOW} lmm wait --in-reply-to ${REQUEST_ID} --timeout 7200
    output: REPORT

handler_on:
  success:
    run: tmac kill ${TASK}
  failure:
    # 作業環境を残し、自動の入力を止めて人へ引き継ぐ
    run: tmac hold ${TASK} --key flow-failed --note "implement が失敗した（${DAG_RUN_ID}）"
```

* エージェントの起動・入力・終了は tmac、メッセージは lmm、手順と失敗時の扱いは Dagu が担当し、互いの内部には立ち入らない。
* 失敗時に `tmac kill` せず保留するのは、未回収の成果と作業環境を人へ引き継ぐためである（vision.md §4.2）。人が確認を終えたら、`tmac release` または `tmac kill --force` で片付ける。

### 13.3. 人の操作

```bash
tmac list                                        # エージェントと状態の一覧
tmux attach -t repo                              # ペインを見る（セッションはプロジェクト名）
tmac hold impl-001 --note "仕様を確認中"         # 自動の入力を止める（実行中の入力が終わるまで待つ）
# hold が成功してから、ペインで直接やり取りする
tmac release impl-001
tmac release impl-001 --key unconfirmed          # 確認できなかった入力を、ペインで確かめた後に解除する
```

## 14. 非機能要件

### 14.1. 動作環境

* Linux と macOS を対象とする。`/bin/sh` と tmux を必要とする。tmux の最低バージョンは、使う機能（`new-window -e`、ペインオプション、`paste-buffer -p`、`if-shell -F`）から実装時に確定する（§15）。
* 単一ユーザーのローカル開発環境で使うことを想定する。

### 14.2. リソース

* 常駐プロセスを持たない。
* `tmac hook` は CLI のイベントのたびに起動されるため、短時間で終える。中継コマンドを除き、tmux のコマンドを実行するのは、状態か保留が変わったとき（ペインオプションの更新）だけとする。

### 14.3. セキュリティ

* 入力するテキストは、シェルや tmux のコマンド文字列に埋め込まず、標準入力で tmux に渡す（§7.3）。制御文字を含むテキストは受け付けない（§7.2）。
* フックの入力（JSON）は、プロンプトの文字列などを含むため、信頼できない入力として扱う。値をシェルのコマンド文字列に埋め込まない。中継コマンドには、標準入力でそのまま渡す。
* 設定と中継コマンドは、利用者が書いた信頼できるものとみなす。
* 環境変数の値と入力したテキストは記録しない（§4.2）。
* 承認の確認（権限のプロンプト）には、自動で応答しない。`waiting` の間は入力しない。
* ペインの操作（貼り付け、送信のキー、閉じる）とシグナルの送信は、名札（§3.5）を確認したペインと、そのペインのプロセスに限る。

### 14.4. 終了コード

| コード | 意味 |
| :--- | :--- |
| 0 | 成功 |
| 1 | 実行時エラー（tmux の操作の失敗、起動の失敗、ファイル I/O エラーなど） |
| 2 | 使い方の誤りまたは設定エラー（`spawn` で tmac 以外のフックが見つかった場合を含む） |
| 3 | 時間切れ（`spawn`、`send`、`wake`、`wait`、`hold`） |
| 4 | エージェントがない（記録がない。`send`・`wake`・`wait` では、`exited` になった場合とインスタンス ID が変わった場合を含む） |
| 5 | 入力できない状態、または保留中（`send --no-wait`、`kill`） |
| 6 | 入力を確認できなかった（`send`・`wake`。入力されたかどうかは不明。`unconfirmed` の保留を設定した） |
| 7 | 入力が拒否された（`send`・`wake`。中継が入力を拒否し、CLI は入力を処理しなかった） |
| 128 + シグナル番号 | シグナルによる中断 |

`tmac hook` の終了コードは §6.5 に従う。

### 14.5. 標準出力と標準エラー出力

* 標準出力には、各コマンドで定めた結果だけを出す。`spawn` の `PROJECT/NAME PANE_ID`、`wait` の状態、`status`・`list` の出力、`tmac hook` の中継コマンドの出力である。
* `tmac hook` の標準出力には、中継コマンドの出力以外を書かない。CLI がフックの標準出力を JSON として読むためである。
* 警告とエラーは、すべて標準エラー出力に出す。

| 旧仕様 | 本書での扱い |

| §2 Profiles | tmac から分離した。起動コマンドと引数は `spawn` の `--` の後で受け取る。CLI ごとの制御はドライバ（§3.2）に組み込む。 |
